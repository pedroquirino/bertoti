#### Problema

> O controle de abastecimento das viaturas da Regional de São José dos Campos do IPEM era realizado inteiramente de forma manual. Os condutores registravam em pranchetas físicas mantidas dentro de cada veículo informações como quilometragem, quantidade de combustível, valor abastecido e identificação do condutor. Ao final de cada período, o Diretor da unidade precisava reunir manualmente todas essas anotações, conferi-las individualmente e consolidar os dados para controle interno e posterior digitação no sistema corporativo SGI. Esse fluxo manual comprometia diretamente a eficiência da gestão da frota, tornando difícil realizar análises comparativas entre viaturas, acompanhar o consumo médio de combustível de cada uma delas ou identificar rapidamente inconsistências nos registros.

#### Solução entregue pela equipe

> Desenvolvido pela SquadTech para o IPEM – Regional de São José dos Campos, o sistema web nasceu com a missão de transformar digitalmente o controle de frota, aposentando de vez os antigos registros manuais em pranchetas físicas. A plataforma centraliza todo o fluxo operacional, permitindo que os condutores realizem lançamentos digitais de saídas de veículos e abastecimentos de forma ágil. Para os gestores, a ferramenta traz um módulo dedicado de validação gerencial e uma central robusta de relatórios analíticos e dashboards exportáveis em PDF, Excel, CSV e Word.

#### Arquitetura em camadas

O backend é organizado em uma arquitetura em camadas para separar responsabilidades de forma limpa: o Controller recebe as requisições HTTP e retorna apenas DTOs para proteger o modelo interno; o Service centraliza as regras de negócio e validações operacionais; o Repository gerencia a persistência com o Spring Data JPA; e as Entities fazem o mapeamento relacional do banco MySQL.

```text

│  Front-end                                   │
│  HTML · CSS · JavaScript                     │
└──────────────────────┬───────────────────────┘
                       │ Requisição HTTP
                       ▼
┌──────────────────────────────────────────────┐
│  Controller                                  │
```

<summary>↩️ Registro de retorno do veículo (Sprint 1, T01)</summary>

```java
public RetornoRespostaDTO registrarRetorno(Integer id, RetornoDTO dto) {
    RegistroSaida registro = registroSaidaRepository.findById(id)
            .orElseThrow(() -> new RecursoNaoEncontradoException("Registro de saída não encontrado."));

    if (!"em_andamento".equalsIgnoreCase(registro.getStatus()))
        throw new RegraDeNegocioException("Esta saída já foi encerrada.");

    if (dto.getKmFinal().compareTo(registro.getKmInicial()) < 0)
        throw new RegraDeNegocioException("KM final (" + dto.getKmFinal()
                + ") não pode ser menor que o KM inicial (" + registro.getKmInicial() + ").");

    if (dto.getDataRetorno().isBefore(registro.getDataHoraSaida()))
        throw new RegraDeNegocioException("Horário de chegada não pode ser anterior ao horário de saída.");

    BigDecimal kmRodados = dto.getKmFinal().subtract(registro.getKmInicial());
    registro.setKmFinal(dto.getKmFinal());
    registro.setKmRodados(kmRodados);
    registro.setDataRetorno(dto.getDataRetorno());
    registro.setStatus("concluido");

    Veiculo veiculo = registro.getVeiculo();
    veiculo.setKmAtual(dto.getKmFinal());   // o hodômetro do veículo acompanha a última viagem
    veiculo.setDisponivel(true);            // devolve o veículo para novas saídas
    veiculoRepository.save(veiculo);
    // ... salva o registro e monta o RetornoRespostaDTO
```

O retorno é o momento em que a prancheta de papel deixa de existir, então o dado precisa entrar consistente. O método bloqueia o fechamento de uma saída já encerrada (evita contar a mesma viagem duas vezes), impede KM final menor que o inicial e horário de chegada anterior ao de saída. Os KM rodados são calculados no servidor, e não enviados pelo cliente, para que o relatório de consumo não dependa de uma conta feita no front-end. Ao concluir, o veículo é atualizado com o novo KM e volta a ficar disponível. Como o método grava o veículo e depois o registro, o próximo passo de melhoria seria envolvê-lo em `@Transactional`, para que as duas gravações aconteçam juntas ou nenhuma aconteça.

<summary>🛡️ Tratamento global de erros da API (Sprint 1, T01)</summary>

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(RegraDeNegocioException.class)
    public ResponseEntity<Map<String, Object>> handleRegraDeNegocio(RegraDeNegocioException ex) {
        return buildResponse(HttpStatus.BAD_REQUEST, ex.getMessage());
    }

    @ExceptionHandler(RecursoNaoEncontradoException.class)
    public ResponseEntity<Map<String, Object>> handleNaoEncontrado(RecursoNaoEncontradoException ex) {
        return buildResponse(HttpStatus.NOT_FOUND, ex.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<Map<String, Object>> handleGenerico(Exception ex) {
        return buildResponse(HttpStatus.INTERNAL_SERVER_ERROR, "Erro interno no servidor.");
    }

    private ResponseEntity<Map<String, Object>> buildResponse(HttpStatus status, String mensagem) {
        Map<String, Object> body = new LinkedHashMap<>();
        body.put("timestamp", LocalDateTime.now().toString());
        body.put("status", status.value());
        body.put("erro", mensagem);
        return ResponseEntity.status(status).body(body);
    }
}
```

Sem um handler central, cada controller teria de tratar suas próprias exceções, e o front-end receberia respostas em formatos diferentes. Com o `@RestControllerAdvice`, as regras de negócio viram HTTP 400, os recursos inexistentes viram HTTP 404 e qualquer erro inesperado vira HTTP 500, todos com o mesmo corpo JSON (`timestamp`, `status`, `erro`), e a mensagem pode ser exibida direto na tela. O cuidado importante está no handler genérico: ele devolve apenas "Erro interno no servidor.", para não expor detalhes internos da aplicação a quem consome a API.

```java
private LocalDateTime resolverDataInicio(String periodo) {
    return switch (periodo) {
        case "hoje" -> LocalDateTime.now().toLocalDate().atStartOfDay();
        case "7"    -> LocalDateTime.now().minusDays(7);
        case "30"   -> LocalDateTime.now().minusDays(30);
        case "ano"  -> LocalDateTime.now().minusYears(1);
        default     -> LocalDateTime.now().minusDays(30);
    };
}

// em gerarRelatorio(String periodo)
BigDecimal totalGasto = abastecimentos.stream()
        .map(a -> a.getValorTotal() != null ? a.getValorTotal() : BigDecimal.ZERO)
        .reduce(BigDecimal.ZERO, BigDecimal::add);

// em construirConsumoVeiculos(...)
double custoPorKm = (totalKm != null && totalKm.compareTo(BigDecimal.ZERO) > 0)
        ? totalGasto.divide(totalKm, 4, RoundingMode.HALF_UP).doubleValue() : 0;
```

Esse é o núcleo do relatório que substitui a consolidação manual feita pelo diretor da unidade. O filtro de período chega como texto simples (`hoje`, `7`, `30`, `ano`) e é convertido em uma data inicial por um `switch`; qualquer valor desconhecido cai no padrão de 30 dias, então um parâmetro inválido não derruba o endpoint. Os valores monetários usam `BigDecimal`, que evita os erros de arredondamento do `double`, e a soma trata campos nulos como zero. No custo por km, a divisão só acontece quando o total de KM é maior que zero, o que evita divisão por zero em veículos sem viagens no período, e o resultado usa 4 casas decimais com arredondamento `HALF_UP`.

```java
private byte[] exportarCsv(RelatorioAbastecimentoDTO relatorio) {
    try (ByteArrayOutputStream saida = new ByteArrayOutputStream();
         CSVWriter escritor = new CSVWriter(new OutputStreamWriter(saida))) {

        escritor.writeNext(new String[]{
                "Data/Hora", "Veículo", "Responsável", "Combustível",
                "Litros", "Valor Total", "KM", "Posto", "Cidade", "NF"
        });

        for (AbastecimentoItemDTO item : relatorio.getAbastecimentos()) {
            escritor.writeNext(new String[]{
                    item.getDataHora()        != null ? item.getDataHora().toString()        : "",
                    item.getVeiculo()         != null ? item.getVeiculo()                    : "",
                    item.getQuantidadeLitros() != null ? item.getQuantidadeLitros().toString() : "",
                    // ... demais colunas, todas com a mesma proteção contra nulo
                    item.getNotaFiscal()      != null ? item.getNotaFiscal()                 : "—"
            });
        }

        escritor.flush();
        return saida.toByteArray();
    } catch (IOException e) {
        throw new RuntimeException("Erro ao gerar CSV.", e);
    }
}
```

O gestor precisa levar o relatório para fora do sistema (planilhas e o sistema corporativo SGI), então o serviço gera o arquivo em memória e devolve `byte[]`, que o controller entrega como download com o tipo de mídia correto. Assim o service não depende de HTTP e a geração fica reaproveitável. O `try-with-resources` garante que o fluxo e o `CSVWriter` sejam fechados mesmo em caso de erro, e cada campo opcional passa por uma verificação de nulo para que uma anotação incompleta (como uma nota fiscal ausente, que aparece como "—") não quebre a exportação inteira. Para o CSV e o Excel usei OpenCSV e Apache POI; o PDF e o Word do mesmo serviço foram desenvolvidos por outros integrantes da equipe.

```java
public UserResponseDTO updateProfile(Integer registration, UpdateProfileDTO dto) {

    User user = repository.findByRegistration(registration)
            .orElseThrow(() -> new ResourceNotFoundException("Usuário não encontrado."));

    if (dto.getName() != null && !dto.getName().isBlank())
        user.setName(dto.getName());

    if (dto.getNewPassword() != null && !dto.getNewPassword().isBlank()) {

        if (dto.getCurrentPassword() == null || dto.getCurrentPassword().isBlank())
            throw new BusinessRuleException("A senha atual é necessária para definir uma nova senha.");

        if (!passwordEncoder.matches(dto.getCurrentPassword(), user.getPassword()))
            throw new BusinessRuleException("A senha atual está incorreta.");

        user.setPassword(passwordEncoder.encode(dto.getNewPassword()));
    }

    return toDTO(repository.save(user));
}
```

O usuário comum precisa corrigir o próprio nome ou trocar a senha sem depender de um administrador. Por isso a atualização é parcial: só altera o que foi enviado. A troca de senha é a parte sensível, então exige a senha atual e a compara com o hash salvo usando `passwordEncoder.matches`, e a nova senha só é gravada depois de passar por `passwordEncoder.encode`. Isso impede que alguém com uma sessão aberta no computador de outra pessoa altere a senha sem conhecê-la e garante que nenhuma senha seja armazenada em texto puro. O endpoint recebe a matrícula pela URL e o corpo vai em um DTO próprio (`UpdateProfileDTO`), então campos como cargo e status não podem ser alterados por essa rota.

</details>

#### Desafios técnicos enfrentados

1. **Mudança da convenção de nomes no meio do projeto** — Em 27/04 renomeei as classes do módulo de abastecimento para inglês, em 29/04 o módulo voltou ao português para acompanhar o restante do código e, em maio, a equipe decidiu padronizar tudo em inglês. Para a última etapa, quebrei a refatoração em 13 commits (`#00.1` a `#00.13`), um por entidade, para que cada revisão fosse pequena e fácil de reverter. O aprendizado foi combinar a convenção de nomes com a equipe antes de começar a codar, e não depois.
2. **Conflitos de merge entre branches de colegas** — Resolvi conflitos ao integrar a T01 na Sprint-1 (01/04) e o módulo A04 na Sprint-2 (01/05), este último com mudanças grandes no `AbastecimentoService`, no `AbastecimentoRepository` e no `pom.xml`. Aprendi a integrar com mais frequência e em partes menores, para que os conflitos sejam pequenos.
3. **Higiene do repositório** — Ao integrar a T01, percebi que os arquivos compilados (`target/`) estavam versionados e que o `application.properties` guardava usuário e senha do banco. Adicionei o `.gitignore`, removi os arquivos de build e esvaziei as credenciais do arquivo de configuração, para que cada integrante use suas próprias credenciais localmente.
